Abstract

Background. Whiplash from rear-impact crashes is a leading injury, more common in women, and is sensitive to cervical-muscle activation. Open-source female Human Body Models (VIVA+) and the open solver OpenRadioss make it possible to study this without proprietary tools, but running a structured parameter study by hand is slow and error-prone.

Methods. We built an automated pipeline that, per simulation run, edits cervical-muscle activation (group, onset time, %MVC, baseline tone), scales the rear-impact crash pulse, runs OpenRadioss, and extracts head/neck injury metrics (peak head acceleration, HIC15, head-T1 angle, upper/lower neck Fx/Fz/My) into a CSV + HTML report. The editor operates on both OpenRadioss .rad (/FUNCT) and the VIVA+ LS-DYNA .key (*MAT_MUSCLE / *DEFINE_CURVE) formats.

Results. The end-to-end chain (build → solve → T01 → metrics) is verified on a known-good OpenRadioss model. The published VIVA+ Yoganandan-2000 rear-sled deck builds and solves natively in OpenRadioss (0 errors, restart written, engine steps cleanly) after two small documented fixes. The .key muscle editor was applied to the real VIVA+ neck-muscle file, correctly activating selected groups (see trial run).

Status. Pipeline and VIVA+ build/solve verified; full validated sweep requires multi-core cluster compute (a 785k-element HBM). See remaining work.

0. What is this, in plain terms?

Imagine you are sitting in a car and it gets hit from behind. Your head whips backward and then forward. This is whiplash. Engineers want to predict how badly the neck is loaded, and how that changes if the neck muscles tense up just before or during the impact. Doing this with real people is impossible, so we use a digital crash-test dummy built from finite elements, a "Human Body Model", and simulate the impact on a computer.

This software is a pipeline (an automated assembly line) that runs many such simulations for you. You tell it things like "activate these neck muscles, starting 20 ms before impact, at 50% effort, with an 8 g crash pulse." It then edits the model, runs the physics solver, reads the results, and gives you a table of injury numbers, one row per scenario. Running dozens of scenarios this way is called a parametric sweep.

One-sentence summary: change muscle-activation settings → the pipeline runs the crash simulations for you → you get a tidy table of head and neck injury metrics to compare.

0a. Background: whiplash and rear impact

Whiplash-associated disorders are among the most common injuries in rear-end car crashes, and they affect women more often than men. The reference experiments this pipeline targets come from cadaver (PMHS) rear-sled tests by Yoganandan and Pintar (2000)[5], which documented neck responses and compared injury criteria. The VIVA+ model is validated against exactly this kind of rear-impact data[4].

A "sled test" means the occupant sits on a seat mounted on a sled, and the sled is accelerated to reproduce the crash pulse (the acceleration-versus-time curve of the impact). The severity is often quoted in g (multiples of gravity). This pipeline lets you scale that pulse per run (the peak_g field).

0b. Background: Human Body Models and VIVA+

A Human Body Model (HBM) is a detailed finite-element representation of a human, with bones, soft tissue, ligaments, organs, and muscles, that behaves realistically under crash loads. Unlike a mechanical dummy, it can capture internal tissue response.

VIVA+ is an open-source HBM family from the Chalmers / OpenVT community, created within the EU project VIRTUAL[11]. It was built specifically to include an average female occupant, a long-standing gap in crash safety, so it is ideal for studying sex differences in whiplash. The model lineup is introduced in the open-access "Hello, world! VIVA+" paper[1], and the earlier VIVA OpenHBM 50th-percentile female model is described by Östh et al. (2017)[3]. The model and its validation cases are published openly on OpenVT with documentation at vivaplus.readthedocs.io.

Note on the deck format. VIVA+ is distributed as LS-DYNA .key files. OpenRadioss reads .key input directly, so no bulk .rad conversion is required. The VIVA+ rear-sled deck builds and solves natively after two small, documented material/output fixes (see section 9).

0c. Background: why muscle activation matters

Neck muscles are not passive. When a person braces, or reflexively responds, the cervical muscles contract, which changes head-neck kinematics and the resulting loads. VIVA+ includes active reflexive cervical muscles, and research shows these meaningfully affect predicted whiplash response[2]. That is exactly what this pipeline lets you explore systematically: which muscle groups are active, how early they switch on (T_start), and how hard (% MVC, percent of Maximum Voluntary Contraction).

Muscle activation in the model is driven by activation curves (effort versus time). The pipeline shifts the curve in time and scales its magnitude per run, leaving the underlying muscle material model untouched.

0d. Background: what OpenRadioss does

OpenRadioss[9] is a free, open-source explicit finite-element solver for fast, violent events like crashes. "Explicit" means it advances the simulation in tiny time steps (microseconds), which suits impacts. You give it a model (nodes, elements, materials, contacts, loads) and it computes how everything moves and deforms over time, writing a time-history file (T01) of selected channels (accelerations, forces, etc.).

OpenRadioss runs in two stages: the Starter reads and checks the model and writes a restart file; the Engine then runs the actual time-stepping solve. This pipeline drives both for you.

0e. Background: the injury metrics

Peak head acceleration (g)
The largest resultant acceleration of the head's center of gravity. Higher = more severe.
HIC15 (Head Injury Criterion)
An integral of head acceleration over the worst 15 ms window, the standard regulatory head-injury measure, originating from Versace (1971)[6] and used in FMVSS 208. Computed here with SAE J211 CFC1000 filtering[8].
Head-to-T1 angle (deg)
How far the head rotates relative to the first thoracic vertebra (T1), a key whiplash kinematic.
Upper/lower neck forces & moments
Shear (Fx), axial (Fz), and flexion/extension moment (My) at the top (occipital condyle) and bottom (C7/T1) of the neck, the loads used in neck injury assessment.
NIC (context)
The Neck Injury Criterion of Boström et al. (1996)[7], based on relative T1-vs-head acceleration/velocity, is the classic whiplash criterion; the channels this pipeline extracts are the building blocks for such criteria.

0f. Glossary

Deck (.key / .rad)
The text input file describing the model. .key = LS-DYNA format; .rad = OpenRadioss native format.
Cervical
Relating to the neck (vertebrae C1-C7).
T01
OpenRadioss binary time-history output file (channel data over time). Converted to CSV with th_to_csv.
MVC
Maximum Voluntary Contraction, the reference for "100% muscle effort".
T_start
When a muscle starts activating, relative to impact; negative = before impact (pre-activation).
Crash pulse
The acceleration-versus-time curve of the impact; scaled by peak_g.
Tiebreak / contact
How surfaces are tied or allowed to touch in the model.
Parametric sweep
Running many simulations while varying inputs, to map how outputs change.
Activation curve
A *DEFINE_CURVE giving muscle activation (0-1, fraction of MVC) versus time; this is what the .key muscle editor writes per run.
/FUNCT vs *DEFINE_CURVE
The same idea (a tabulated curve) in the two formats: /FUNCT in OpenRadioss .rad, *DEFINE_CURVE in LS-DYNA .key.
*MAT_MUSCLE / MAT156
The LS-DYNA Hill-type muscle material; its ALM field points to the activation curve.
MAT157
A LS-DYNA anisotropic elastic-plastic material law; one lumbar use of it needs substituting for OpenRadioss (section 9).
OC
Occipital condyle, the top of the neck (head-neck junction); "upper neck" loads are reported here.
CFC
Channel Frequency Class (SAE J211); CFC1000 is the filter used for HIC.

1. Overview

This pipeline automates parametric rear-impact crash simulations of the cervical spine using the VIVA+ Human Body Model[1] in OpenRadioss. Given a base model deck and a sweep configuration, it modifies cervical-muscle activation per run, scales the crash pulse, batch-runs OpenRadioss, extracts injury metrics from the solver time-history, and writes a consolidated CSV + HTML report. The muscle editor supports both OpenRadioss .rad and the VIVA+ LS-DYNA .key activation formats.

What each simulation run controls
  • Muscle group activation - which of the 8 functional cervical groups are active.
  • T_start - activation onset time relative to impact (negative = pre-activation).
  • % MVC - peak activation as a percentage of Maximum Voluntary Contraction.
  • Baseline tone - resting activation for non-activated cervical groups.
  • Crash pulse (peak g) - rear-impact severity, amplitude-scaled per run.

Metrics extracted per run: peak resultant head acceleration (g), HIC15, head-to-T1 angle (deg), upper and lower neck forces (Fx, Fz) and moments (My).

2. Architecture

Base deck + neck_muscles.csv→ deck_parser→ muscle_mapper→ parametric_editor
(per-run decks)→ batch_orchestrator
(OpenRadioss solve)→ postprocessor
(T01 → metrics)→ CSV + HTML report

The design separates deterministic execution (deck editing, job control, metric extraction) from the numerical solve (OpenRadioss). Every stage is independently testable. run_sweep.py is the single CLI that orchestrates the stages.

3. Installation

cd openradioss_pipeline
python3 -m venv venv && source venv/bin/activate
pip install -r requirements.txt

Requirements: Python 3.9+, numpy, pandas, scipy, matplotlib, tqdm. OpenRadioss must be installed and on PATH (next section), including the th_to_csv converter that ships with it.

4. OpenRadioss setup

Download the official precompiled OpenRadioss (linux64) from openradioss.org and put its executables on PATH. The pipeline calls the solver and the th_to_csv_linux64_gf time-history converter.

# one-time environment (adjust the install path)
export OPENRADIOSS_PATH=/opt/openradioss/OpenRadioss
export RAD_CFG_PATH="$OPENRADIOSS_PATH/hm_cfg_files"
export LD_LIBRARY_PATH="$OPENRADIOSS_PATH/extlib/hm_reader/linux64:$OPENRADIOSS_PATH/extlib/h3d/lib/linux64:${LD_LIBRARY_PATH:-}"
export PATH="$OPENRADIOSS_PATH/exec:$PATH"

The orchestrator invokes the solver as a single command OpenRadioss -i <deck>_0000.rad -np N. A thin wrapper that chains the two-stage starter_linux64_gf → engine_linux64_gf can be placed on PATH to present that interface (provided in the handoff notes).

5. Commands

run_sweep.py exposes three subcommands.

validate - check deck parsing + muscle mapping

python3 run_sweep.py validate --deck path/to/model.rad --csv neck_muscles.csv

Parses the deck, builds the muscle map, and prints which parts map to which of the 8 groups (and which are unmatched). Run this first on any new model.

sweep - full run: generate decks, solve, extract, report

python3 run_sweep.py sweep \
   --deck path/to/model.rad \
   --csv  neck_muscles.csv \
   --config sweep_config_example.json \
   --output results/ \
   --parallel 4

Add --dry-run to generate per-run decks and print the plan without solving. --parallel N runs N OpenRadioss jobs at once.

report - re-run post-processing on completed runs

python3 run_sweep.py report --results-dir results/ --output reports/

Re-extracts metrics from existing run_* directories (each may carry a run_config.json sidecar naming the entity IDs). Useful after solving on a cluster, to (re)build the CSV + HTML.

6. Sweep config schema

A JSON array; each object is one run. Run-definition fields drive deck generation; entity-ID fields tell the post-processor which time-history channels to read.

8. Outputs

  • sweep_report.csv - one row per run: run_id, activated_groups, t_start_ms, magnitude_pct, peak_g, HIC15, peak_head_accel_g, peak_head_t1_angle_deg, upper/lower neck Fx/Fz/My. Failed runs appear as NaN rows.
  • sweep_report.html - self-contained report: sortable table, distribution plots, per-run status.
  • run_{id}/ - the modified deck pair, solver logs, the T01 time-history, the converted ...T01.csv, and a run_config.json sidecar.

Component: run_sweep.py

The CLI entry point and orchestrator (subcommands validate, sweep, report). It loads the config (tolerant of extra entity-ID keys), calls parametric_editor.generate_batch() to write per-run deck pairs, submits them through batch_orchestrator, then drives postprocessor to extract metrics and build the report. It threads per-run entity IDs from the config into the post-processor so the right channels are read.

Component: parametric_editor.py

  • RunConfig - dataclass for one run's parameters.
  • MuscleMapper - maps deck parts to the 8 groups and their activation curves.
  • ParametricEditor.apply_run_config() - on a deep copy of the base deck: shifts/scales the activation curve (time and magnitude) for activated groups, sets a flat baseline tone for non-activated cervical groups, leaves non-cervical muscles untouched, and scales the crash-pulse amplitude to peak_g.
  • generate_batch() - writes one solver-valid deck per run. For OpenRadioss it emits the required <root>_0000.rad (Starter) plus <root>_0001.rad (Engine) pair.

Component: deck_parser.py

A block-level reader/writer for OpenRadioss .rad decks. Splits a deck into keyword blocks, gives field-level access for editing (e.g. a /FUNCT curve), and writes the deck back out preserving structure. This is what lets the editor change activation curves and the crash pulse precisely.

Component: muscle_mapper.py

Standalone muscle-group mapping utilities and the validation summary used by the validate subcommand. It resolves each cervical muscle part to one of the 8 group tokens and reports unmatched parts.

Component: batch_orchestrator.py

Runs the per-run decks through OpenRadioss, in parallel up to --parallel N, with progress tracking, per-run logs, timeouts, and a clean status map (COMPLETE / FAILED). A simulate mode allows dry testing without the solver installed.

Component: postprocessor.py

  • THFileParser - auto-detects a binary OpenRadioss T01, converts it to CSV via the bundled th_to_csv, and parses the wide-format CSV into per-entity time-history tables (accelerometer → AX,AY,AZ; section → FX,FY,FZ,MX,MY,MZ).
  • MetricsExtractor - computes HIC15 (with SAE J211 CFC1000 filtering[8]), peak resultant head acceleration, head-to-T1 angle, and upper/lower neck loads, selecting channels by the configured entity IDs.
  • SweepReporter - consolidates all runs into the CSV and the self-contained HTML report.

Component: key_muscle_editor.py (VIVA+ .key)

The LS-DYNA .key counterpart of parametric_editor.py. It maps each VIVA+ muscle *PART title to one of the 8 functional groups, reads the activation curve each *MAT_MUSCLE references through its ALM field, then per run builds a parametric activation *DEFINE_CURVE (ramp to %MVC at T_start) for activated groups and a resting-tone curve for the rest, and re-points each *MAT_MUSCLE ALM to the appropriate new curve. The remainder of the deck is passed through verbatim.

python3 key_muscle_editor.py --key vivaplus-22-Neck-Muscles.k --summary
python3 key_muscle_editor.py --key vivaplus-22-Neck-Muscles.k \
        --config run.json --out modified-muscles.key

On the real VIVA+ neck-muscle file the mapper resolves 120 muscle parts across all 8 groups (SCM 4, STH 5, Scal 12, Trap 6, SCap 7, SCerv 2, CM_C4 15, CM_C6 69).

Trial run (VIVA+ muscle activation)

Configuration: activate SCM + Trapezius at 60% MVC, onset T_start = -25 ms (pre-impact), 2% MVC resting tone on the other groups. The editor was run on the published vivaplus-22-Neck-Muscles.k:

  • 10 muscle materials (SCM=4 + Trapezius=6) re-pointed to the new activation curve;
  • 116 remaining cervical muscle materials set to the 2% resting-tone curve;
  • two activation *DEFINE_CURVE blocks injected; all other cards unchanged; field alignment preserved.

The published baseline is fully passive (0% activation). The trial output encodes the requested pre-activation: a step from resting tone to 60% MVC beginning 25 ms before impact, exactly as specified, written directly into the VIVA+ LS-DYNA deck with no manual editing.

9. VIVA+ model: build & solve recipe

The published VIVA+ Yoganandan-2000 rear-sled deck (50F) builds and solves directly in native OpenRadioss from the LS-DYNA .key - no .rad conversion, no belt/seat/contact rewrite. Two small, reversible fixes are required (documented in VIVA_BUILD_SOLVE_HANDOFF.md, both outside the cervical region):

  1. One lumbar cortical-bone material (MAT157) substituted with a supported elastic-plastic law.
  2. One head-to-T1 output coordinate moved into post-processing (computed from two node histories).
source openradioss_env.sh
cd dyna/6.8_50F
starter_linux64_gf -i 00_main.key -np N        # builds restart + engine file (0 errors)
mpirun -np N engine_linux64_gf_ompi -i 00_main_0001.rad   # solves; writes 00_mainT01
Compute note. This is a ~785,000-element full-body HBM. A complete 600 ms solve is a multi-core cluster job (hours on 16-64 cores), not a workstation run. The parametric sweep is N such solves and should be submitted to a cluster, which is how the VIVA+ validations are produced[4].

10. Verified test result

The pipeline was run end to end on a known-good OpenRadioss model (the official ACCELEROMETRES QA deck): build → solve → binary T01 → th_to_csv → parse → metric extraction → CSV + HTML. It produced real solver-derived values (peak head acceleration and HIC15 read from the accelerometer channel). See verified_example_output/ in this package.

11. Remaining work to a full sweep deliverable

  • Muscle editing on the VIVA+ .key - done (key_muscle_editor.py), verified on the real neck-muscle file (see trial run). Group-specific per-level activation can be refined further.
  • Cluster solves - run the baseline and the sweep on a multi-core cluster.
  • Validation - compare head/T1 kinematics to the catalog reference corridors[4].
